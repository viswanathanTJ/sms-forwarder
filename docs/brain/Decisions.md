# Decisions made during the v2 build

Rulings taken by the build controller on the owner's behalf (2026-10-25), each with why and what it costs if wrong. See [[00 Index]], [[Known Issues]].

- Ruling 1: T1 may delete old `ui/screen/*` settings UI and must strip cloud calls from SMSReceiver/MainActivity so the app builds; UserPreferences + old service stay until T10/T12 — why: plan says build must pass after T1 — cost if wrong: v1 settings screen gone between T1 and T12 on dev builds only.
- Ruling 2: T11's V1MigrationRunner must reuse the single existing v1 `Context.dataStore` delegate (no second delegate for "settings"); T12, when deleting UserPreferences/old UI, moves that delegate into V1MigrationRunner.kt — why: DataStore forbids two active instances per file — cost if wrong: crash on first v2 launch.
- Ruling 3: missed-call smart line uses the carrier display name when BankSenderResolver/classifier resolves one, else the raw sender ID; the T6 test with sender "JM-AIRTEL" asserts the plan's exact string "via JM-AIRTEL" — why: plan pins exact strings and Airtel is not a bank — cost if wrong: cosmetic.
- Ruling 4 (T4): Spam (SCAM / inSpamStore) checked before OTP in MessageAnalyzer — why: spec anti-goal 'never forward scams'; spec 5.1 lists Spam as its own source — cost if wrong: a genuine OTP flagged SCAM by the classifier is not forwarded (visible in Log as Spam).
- Ruling 5 (T4): zero-amount TRANSACTION downgraded to IMPORTANT also nulls Analysis.txn — why: Task 6 formatter must not render a transaction for a non-transaction — cost if wrong: none visible.
- Ruling 6 (T4): Spam-before-OTP ordering is defensive (classifier already returns PROMOTIONAL+SCAM for scam OTPs with autoFilterSpam=true); scamOtp test pins the end behaviour, not the ordering — why: forcing reachability would change classifier options — cost if wrong: none today.
- Ruling 7 (T5): loop guard removing all sends of matched rules → matchedRuleIds kept, sends empty, skip null (not NO_RULE); PhoneNumbers.normalize = last 10 digits for 10+ digit strings, alnum IDs uppercased unchanged — why: brief silent; Log must distinguish "no rule" from "matched but guarded" — cost if wrong: Log wording.
- Ruling 8 (T5): CONTACTS_PERMISSION_MISSING only when an enabled, type-matching rule with destinations was excluded solely by its sender condition for an UNVERIFIED sender; otherwise NO_RULE — why: Log reason must be truthful (personal msgs with no rule are "no rule", not a permission problem) — cost if wrong: misleading Log text. To be applied in fix round.
- Ruling 9 (T6): MessageAnalyzer.senderName = BankSenderResolver name for any business sender when known, else canonical ID title-cased; phone numbers raw — why: plan's formatter strings need "Amazon" for AD-AMAZON — cost if wrong: cosmetic sender names.
- Ruling 10 (T6→T8): Dispatcher/TelegramClient must guard: blank text → send original body instead; final Telegram text hard-capped at 4096 — why: closes T6 minors 3 and 6 at the send boundary — cost if wrong: one failed send.
- Ruling 11 (T7): LogEntity gets nullable `otpCode` column (cleared on masking); Counts semantics: forwarded = ≥1 SENT outbox row, skipped = skip reason or no outbox rows, retrying = any PENDING row — why: brief silent — cost if wrong: Home counts wording.
- Ruling 12 (T7): fix round also includes TokenCipher @Synchronized key creation + decrypt-without-key → null; resend only FAILED rows; brain note on untested DAO SQL — why: token loss / duplicate sends are user-visible — cost if wrong: none.
- Ruling 13 (T7→T9): IncomingProcessor must write the log row's decision and its outbox rows in one Room transaction; T9 must set catchUpFloor at first run (masterOn default true, floor default 0) — why: crash between steps loses a message; Review Focus 5 — carry into T9/T11 dispatch.
- Ruling 14 (T7→T8/T10): Dispatcher and ProblemAlerter must tolerate outbox rows / alertsDestinationId pointing at deleted destinations (mark FAILED "destination removed"; fall back to first Telegram destination) — carry into T8/T10.
- Ruling 15 (T8): delivery work = unique one-time "delivery", REPLACE, NetworkType.CONNECTED (SMS rows also wait for network — accepted), delay = earliest pending nextAttemptAt − now — why: plan text was self-contradictory; REPLACE tracks earliest due — cost if wrong: SMS retries wait for data network.
- Ruling 16 (T8): per-destination strict order by firstAttemptAt; Retry on a row blocks that destination's newer rows for the pass; Sent unblocks the destination's pending rows immediately; deliver under NonCancellable; skip enqueue when delivery worker RUNNING — why: Review Focus 4 + no duplicates — cost if wrong: one slow destination's rows wait together.
- Ruling 17 (T8): blank/undecryptable token → Fatal("Bot token not set"); unique SMS request codes across restarts; consistent `now` — why: avoid 24 h silent loops / stale PendingIntent reuse — cost if wrong: none.
- Ruling 18 (T8): ensureActive per row; inline schedule() while worker RUNNING enqueues APPEND_OR_REPLACE follow-up (worker end-of-pass keeps REPLACE); .fuse_hidden* gitignored — why: no stranded rows before T10 watchdog — cost if wrong: one extra worker run.
- Ruling 19 (T9): InboxCatchUp treats catchUpFloor == 0 (unset) as "first run": set floor = now and process nothing — why: Review Focus 5 (never forward history on fresh install even before T11 migration exists) — cost if wrong: messages received before first ever app start are not forwarded.
- Ruling 20 (T9): decide first, then single transaction: insert full LogEntity (IGNORE) + outbox rows; no placeholder — why: Ruling 13's loss window; reorders brief's insertIfNew-first — cost if wrong: duplicate analysis work by race loser only.
- Ruling 21 (T9): LogEntity.looseKey (sender|bodyHash) indexed; CATCH_UP rows with date_sent ≤ 0 skipped if same looseKey within ±120 s of inbox date — why: SMS apps not writing date_sent would double-forward — cost if wrong: two identical texts from same sender within 2 min via catch-up only → one dropped.
- Ruling 22 (T10): watchdog has no network constraint; alerts skipped (state untouched) when no Telegram destination exists; FGS start failures fall back to watchdog — why: offline expiry + no lost alerts — cost if wrong: none.
- Ruling 23 (T10): new Problem PAUSED "Forwarding is switched off" alerted while masterOn=false; other alerts continue while paused — why: owner manages elder phones remotely; spec silent — cost if wrong: one extra Telegram alert when owner pauses deliberately.
- Ruling 24 (T11): don't delete v1 store file while delegate open — clear migrated/cloud keys instead (keep any key update/ needs); awaitDone() gate before processing/service/watchdog read rules; fresh install masterOn=false — why: DataStore single-instance + startup race — cost if wrong: stale v1 file remains (harmless).
- Ruling 25 (T11): migrationDone set before destructive v1 clear; no fresh-install settings writes when rules exist; pure V1Migration.steps decision tested — why: idempotency — cost if wrong: v1 keys may linger (harmless).
- Ruling 26 (T12): when deleting UserPreferences, move update/'s STORED_UPDATE storage to SettingsStore (settings_v2) and move the v1 `Context.dataStore` delegate into V1MigrationRunner.kt (only reader) — why: Ruling 2 + plan says delete UserPreferences — cost if wrong: one-time loss of cached update info (re-fetched).
- Ruling 27 (T13): amounts shown as ₹1,250 (Money.format strips .00, SMS-app en_IN convention) instead of spec sample ₹1,250.00 — why: spec sample illustrative; ported formatter pinned by tests — cost if wrong: cosmetic.
- Ruling 29 (T14): Home tiles = Forwarded / Skipped / "Not sent" (Retrying+Failed), each log in exactly one bucket via the same deliveryState as the Log chip — supersedes Ruling 11 counts semantics — why: consistency — cost if wrong: tile label differs from mock ("Retrying").
- Ruling 30 (final fix wave): when prune masks an OTP log, its still-PENDING outbox rows must be marked FAILED "OTP expired (not sent within 1 hour)" instead of later sending masked text — why: masked OTP delivery is useless/misleading — cost if wrong: OTPs delayed >1 h are not delivered (stale anyway).
- Ruling 31 (T15): PIN = SHA-256(salt+PIN) with per-install salt, unlock until backgrounded; onboarding final step "Start forwarding" (floor=now, masterOn, start); Test-a-message in-memory only; READ_PHONE_STATE requested lazily for SIM picker — why: security + fresh-install paused default — cost if wrong: extra permission prompt.
- Ruling 32 (T15): PIN back-off after 5 wrong tries 30 s doubling to 5 min — why: 4-digit PIN brute force — cost if wrong: owner waits after typos.
- Ruling 33 (final): v1 users lose "forward everything" after upgrade (v2 default rules only) — kept per spec 5.10; must be stated in release notes. "Unknown senders" rule exists disabled for them to switch on.
- Ruling 34 (final): first destination added auto-attaches to default rules without destinations and enables OTPs/Bank/Missed calls — why: owner sets up and taps Start; nothing forwarding silently is the worst outcome — cost if wrong: one unexpected rule enablement (visible on Home).
- Ruling 35: the new Important + minors 2–3 are folded into Task 16's still-open device-step dispatch as a code pre-step (state guards on markRetry/markFailed/markSent; re-read row state before deliver; Clear deletes only receivedAt < floor) — why: no second final fix wave, but Task 16 is not complete and these are load-bearing for Ruling 30 — cost if wrong: one more scoped review. Minor 4 (re-attach after delete-all) parked → Known Issues.
